## 발견하여 수정한 문제

YouTube 연결 해제 시 미완료 작업만 취소하고 완료 작업의 외부 목록 ID·항목을 보관하던 동작을 수정했다. 연결 해제·권한 무효 확인 시 동의 요청과 모든 내보내기 기록을 제거한다. access 토큰은 즉시 지우고 철회 재시도에 필요한 암호화 refresh 토큰만 유지한다. 철회 성공 시 잔여 자료를 삭제하며 이전 generation의 철회 결과가 새 연결 자료를 지우지 않도록 한다.

회귀 검증은 완료 작업 삭제, 다른 계정 보존, 늦은 작업자 응답의 자료 재생성 방지, 오래된 철회 결과의 새 연결 보존, 철회 실패 시 회원 유지까지 포함한다. 수정 코드는 이번 변경에 포함하며 운영 반영은 별도 배포 이후에 확인한다.

## 외부 백업 준비

카드 등록 없는 Backblaze B2용 업로드·다운로드·암호화·버전별 만료 정리를 준비했고 10월 7일 GitHub 작업을 활성화했다. [계정·저장소와 활성화·검증 기록](offsite-backup.md)을 따른다. 저장소 모의 응답 검증과 실제 클라우드 업로드를 구분한다.

회원 자료의 운영 복구는 완전한 탈퇴 기록을 확보해야 공개 재개할 수 있다. 시험용 UUID 기록은 전체 운영 탈퇴 기록의 완전성을 증명하지 않는다. 현재 복구 스크립트는 이 확인이 없으면 복구를 거부하고, 성공해도 `readyForPublicTraffic=false`로 남긴다.

## B2 실제 연결 검증

버킷 `stelody-backups`와 `stelody/backups/` 경로에 제한된 키를 확인했다. 공개 ACL이 없고, 접두어의 숨김 1일·이전 버전 삭제 1일 규칙이 활성화된 것을 API로 읽었다. 개인정보 없는 시험 파일을 암호화해 업로드하고, 다운로드·복호화 원본 일치와 익명 접근 401을 확인했다. 같은 키의 만료된 이전 버전을 VersionId로 영구 삭제하고 미만료 버전이 남는 것도 확인했다. 시험 파일의 모든 버전은 정리했다.

이 10월 5일 시험은 실제 일일 수명 주기 작업과 GitHub 예약 백업 실행을 확인한 결과는 아니다. 당시 복구용 운영 키와 GitHub 등록용 값은 무시되는 비공개 로컬 파일에만 준비했으며 개인키는 GitHub 등록용 값에서 제외했다.

10월 5일 운영 DB에서 새로 만든 백업(817599 bytes)을 운영 복구 공개키로 암호화해 B2에 임시 업로드했다. 내려받아 복호화한 PostgreSQL 덤프가 원본 바이트 및 checksum과 일치했고 `pg_restore --list`로 archive를 검증했다. 운영 DB 복원은 하지 않았다. 검증 후 원격 파일의 모든 버전과 로컬 평문·시험 접속 자료를 제거했다. 이때 자동 예약 백업은 비활성이었다.

## GitHub 자동 백업 활성화 — 2026-10-07

사용자 승인 후 `production-backup` environment의 Secrets 6개·변수 3개를 등록하고 `main` 브랜치만 사용할 수 있게 제한했다. 저장소 변수 `BACKUP_ENABLED=true`를 적용했다. 운영 복구 개인키는 GitHub에 등록하지 않았다.

[첫 수동 실행 #11](https://github.com/MinHyukJi1226/Stelody/actions/runs/37609917358)은 KST 19:49에 시작해 1분 16초 후 성공했다. 운영 DB 백업, age 암호화, 비공개 B2 업로드, VersionId를 지정한 암호문 무결성 확인, 실행기의 임시 자료 정리를 확인했다.

그 B2 파일을 실제로 내려받아 복호화한 뒤 외부 네트워크와 공개 포트가 없는 별도 PostgreSQL 17 컨테이너에서 `pg_restore`와 정리 SQL로 검증했다. 공개 360곡·11멤버·V19, 제외 대상 14개 테이블의 행 0개, 자동 공개 비활성 및 조회수 공개 포인터 초기화를 확인했다. ACL도 복원했다. 시험 DB와 로컬 평문·다운로드 파일은 제거했고 실제 B2 백업은 보관했다.

완전한 운영 탈퇴 기록을 만들거나 서비스를 중단했다고 가정하지 않았다. `complete=false` 기록의 거부를 확인했으며 이 오프라인 archive 시험은 `database.py restore`를 이용한 전체 운영 복구·트래픽 재개 완료를 뜻하지 않는다. 첫 예약 실행, B2 일일 수명 주기 삭제 관찰과 독립 탈퇴 기록 확보는 남아 있다.

운영자는 복구 개인키의 Mac 외부 사본을 보관했다고 확인했다. 보관 위치와 사본 내용은 수집하지 않았으며 외부 사본 자체의 복호화 시험은 수행하지 않았다.

## 독립 탈퇴 기록 구현 준비 — 2026-10-07

탈퇴 DB 삭제의 확정 전에 최소한의 삭제 의사를 age로 암호화해 B2에 저장하고 정확한 객체 버전을 다시 읽는 경로를 추가했다. 저장 실패 시 탈퇴 503·DB 취소·재시도, 동시 탈퇴 한 번 기록, 다른 연결에서 삭제가 아직 보이지 않는 순서와 기록 후 DB 확정 실패를 PostgreSQL 통합 시험으로 확인했다. B2 저장은 이 시험에서 모의 객체를 사용했으며 실제 운영 버킷을 변경하지 않았다.

복구용 도구는 기록 시작 기준 이전 백업, 상충하는 버전·변조·잘못된 보존 규칙·불명확한 숨김 표시·중지 후 기록을 거부한다. 정상 만료로 숨겨진 오래된 기록은 현재 백업 복구를 막지 않는다. 운영자가 연속 기록과 모든 변경 경로의 중지를 확인한 경우에만 기존 복구 가드용 삭제 목록을 생성한다.

로컬 ARM64 Docker 이미지 빌드, UID 10001, 이미지의 age 1.0.0 암호화와 로컬 복구 도구의 복호화 호환성을 외부 네트워크 없는 컨테이너에서 검증했다. 검증 이미지와 시험 키는 정리했다. Render의 실제 새 릴리스 기동은 아직 수행하지 않았다.

[활성화 절차](withdrawal-journal.md)에 전용 Private B2 버킷·키·8일 숨김/1일 삭제 규칙·Render 설정·기록 시작 기준과 새 백업 순서를 적었다. 이 준비 단계에서는 운영 기능이 비활성이었다. 이후 실제 활성화 결과는 다음 기록을 따른다. 기존 백업의 탈퇴 기록 완전성을 소급 확인한 결과는 아니다.

## 독립 탈퇴 기록 운영 활성화·복구 시험 — 2026-10-07~08

사용자 승인 후 별도 Private 버킷 `stelody-withdrawals-minhyukji1226`, `stelody/withdrawals/`에 제한된 새 키와 환경 변수 7개를 Render에 저장했다. 기록 경로만 8일 후 숨김·숨김 후 1일 삭제 규칙을 적용한 것을 B2 API로 확인했다. 개인키는 Render·GitHub에 전달하지 않았다. Render의 PR #25 릴리스 `d04f580` 재배포와 활성화된 인스턴스 기동을 확인했다.

웹·수집기를 일시 중지하고 직접 DB 수정 중단에 대한 운영자 확인을 받았다. DB 소유자의 읽기 전용 조회에서 커스텀 역할 연결·트랜잭션 0개를 확인한 뒤 필수 확인 플래그로 최초 시작 기준을 저장했다. 기준 시각은 **2026-10-07 23:54:01 KST**다. 이 시각 이전 백업에는 기록 완전성을 소급 적용하지 않는다.

새 `example.invalid` 시험 계정과 합성 세션으로 운영 API에서 즐겨찾기·개인 목록 저장, 재인증 없는 탈퇴 409를 확인했다. [백업 #13](https://github.com/MinHyukJi1226/Stelody/actions/runs/37641133517)은 같은 날 23:58:46 KST에 만들어진 운영 백업을 암호화·업로드했다. 이 파일을 내려받아 복호화·체크섬 일치를 확인한 뒤 시험 계정에만 합성 재인증 자료를 준비해 운영 탈퇴 204, 계정·개인 자료 삭제, 이전 세션 401을 확인했다. B2의 동일 시험 기록을 복호화해 기록 집합과 8일 보존 메타데이터도 확인했다. 실제 Google 재인증 왕복을 시험한 결과는 아니다.

다시 모든 변경 경로를 중지·확인한 상태에서 `withdrawals.py reconcile --confirm-continuous-recording`으로 삭제 목록을 만들었다. 실제 CLI는 결과 저장에 `Path.open`이 지원하지 않는 `opener` 인자를 사용해 실패했으며, `os.open`의 배타적 생성과 명시적 600 권한으로 수정했다. CLI 결과를 기존 복구 가드가 받아들이는 시험과 기존 파일을 보존하는 회귀 시험을 추가했다.

외부 네트워크·공개 포트가 없는 별도 PostgreSQL 17 컨테이너에서 원본 백업에 시험 계정이 존재하는 것을 확인했다. 다른 이름의 빈 DB에 공식 복구 CLI와 실제 B2 대조 결과를 적용한 뒤 시험 계정·즐겨찾기·개인 목록 0개, 공개 360곡·11멤버 유지, 제외 대상 14개 테이블 0개를 확인했다. 복구 대상에는 백업 ACL이 참조하는 `stelody_migrator`, `stelody_app`, `stelody_collector`, `stelody_operator` 역할을 미리 준비했다. 실제 운영 DB에는 복구하지 않았다.

시험 후 Render 서버와 GitHub 수집기를 재개하고 운영 health HTTP 200·UP을 확인했다. 전용 복구 컨테이너, 내려받은 백업·복호화 평문·삭제 목록·합성 세션·진단 파일을 정리했다. 실제 암호화 B2 백업과 탈퇴 기록은 보존 규칙에 따라 유지하며 기록 시작 기준도 유지한다. Git에서 무시되는 로컬 Render 설정은 실제 활성화 값으로 맞췄다.

## 예약 백업 재시도·실패 알림 수신 확인 — 2026-10-08

Render는 PR #26의 `77639f8`을 마지막 성공 배포·Live로 표시했고, 공개 health는 HTTP 200·UP이었다.

[Database backup #17](https://github.com/MinHyukJi1226/Stelody/actions/runs/37766791691)은 예약 실행으로 생성됐지만 `production-backup` 배포 승인 대기 상태에 머물렀다. 현재 환경 설정에는 필수 승인자·대기 타이머가 없고 허용 브랜치는 `main`이었다. 원인은 확정하지 않았으며 보호 규칙을 변경하지 않았다. 운영자의 명시적 승인 후 작업 시작 전 실행을 취소하고 동일 실행을 재시도했다. 두 번째 시도는 KST 22:32에 시작해 1분 29초 후 성공했으며 새 백업 생성·age 암호화·B2 업로드·정확한 객체 버전 읽기 검증·임시 파일 정리를 확인했다. 이는 예약 실행의 수동 재시도 결과이며 다음 무인 예약 실행의 성공을 확인한 결과는 아니다.

B2 읽기 전용 조회에서 비공개 버킷과 백업 접두어의 1일 후 숨김·숨김 후 1일 뒤 삭제 규칙을 확인했다. 기존 백업의 실제 수명 주기 삭제는 아직 관찰하지 않았으며 검증을 위해 보존 시각을 바꾸거나 백업을 직접 삭제하지 않았다.

[실패 알림 시험 #1](https://github.com/MinHyukJi1226/Stelody/actions/runs/37784982475)은 `test/infra-failure-notification` 브랜치의 `36ae9c9`에서 KST 22:31에 실행됐다. checkout·Secrets·운영 환경 접근·예약 없이 `permissions: {}`인 단일 작업에서 의도한 `exit 1`로 실패했다. 운영자는 해당 시험의 실패 알림 이메일 도착을 확인했다. 시험 파일은 main에 포함하지 않았으며 승인된 로컬·원격 시험 브랜치를 정리했다.

## 실제 Google 재인증·탈퇴 확인 — 2026-10-08

운영자가 별도 Google 시험 계정으로 평소 사용하는 브라우저에서 로그인한 뒤 직접 API 검증 코드를 실행했다. 최초 `reauthenticated: false` 보고의 원인은 확정하지 않았다. 이후 명시적인 시작 요청은 HTTP 200이었으며, 읽기 전용 DB 조회에서 KST 22:49:31에 PENDING 상태를 확인했다. 같은 브라우저에서 응답의 Google 인증 주소로 이동하고 동일 시험 계정을 선택한 뒤, 운영자가 `reauthenticated: true` 화면을 제공했다. DB에서도 KST 22:52:03에 CONFIRMED 상태와 KST 22:55:51까지의 유효 시각을 확인했다. 서버 세션·쿠키·토큰을 추출하거나 합성 재인증 자료를 만들지 않았다.

검증 코드는 동일 시험 계정의 ID·일반 회원 권한·유효 재인증을 확인한 뒤 브라우저 확인창을 표시했다. 운영자가 탈퇴를 확정하고 `withdrawalStatus: 204`, `afterStatus: 401`을 보고했다. 별도 읽기 전용 조회에서 해당 계정의 회원·즐겨찾기·플레이리스트·재인증·세션 잔여 행 수가 모두 0임을 확인했다. 이번 시험 계정에 개인 목록이나 즐겨찾기를 새로 만들지는 않았으므로, 이 결과가 새 개인 자료의 삭제 시험을 추가로 수행했다는 뜻은 아니다. 개인 자료가 존재하던 시험 계정의 삭제는 10월 7일 검증 기록에 포함돼 있다.

비공개 탈퇴 기록 버킷에는 KST 22:53:22에 생성된 새 407바이트 객체가 있었으며, 정확한 객체 버전의 age 암호화 헤더·형식 1 메타데이터·10월 16일 KST 22:53:21의 8일 보존 만료 시각을 확인했다. 이번에는 기록을 복호화하거나 운영 DB에 복원하지 않았다. 기존 비공개 설정과 records 접두어의 8일 후 숨김·숨김 후 1일 뒤 삭제 규칙도 유지됐다.

이번 운영 검증에서 실패 알림 실제 수신과 Google 재인증·탈퇴 흐름을 마쳤다. 예약 백업의 수동 재시도도 성공했으며, 다음 무인 예약 실행과 보존 기간이 지난 객체의 실제 수명 주기 삭제는 시간 경과 후 관찰할 항목으로 남는다. 프론트 개발·신규 곡 자동 공개·Google 심사 제출·예약 수집 지연 원인 조사는 이번 변경에 추가하지 않았다.
