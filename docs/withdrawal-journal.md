# 운영 DB와 독립된 탈퇴 기록

탈퇴 완료 후 오래된 백업을 복원해도 계정과 개인 목록이 다시 나타나지 않도록, 탈퇴 요청을 별도 비공개 B2 버킷에 암호화해 기록한다. 기본 설정은 비활성이다. **이 문서의 구성을 실제 운영에 적용하기 전에는 독립 기록의 완전성을 보장하지 않는다.** 기존 백업·수집 설정은 이 기능을 켜지 않는다.

## 처리 순서와 실패

1. 같은 계정의 Google 재인증, 작업 잠금, YouTube 연결 철회를 기존 절차대로 확인한다.
2. DB 트랜잭션 안에서 계정과 개인 자료를 삭제한다. 아직 다른 연결에서는 삭제가 보이지 않는다.
3. 저장소의 비공개 상태·보존 규칙·기록 시작 기준을 검사한다. 회원 UUID·요청 시각·기록 UUID·기록 집합 UUID·형식 번호만 age로 암호화한다. 이메일·Google 식별자·토큰은 기록하지 않는다.
4. 무작위 기록 UUID로 파일을 저장하고 반환된 **동일한 객체 버전**을 다시 읽어 암호문과 메타데이터가 일치하는지 확인한다. 파일명과 메타데이터에는 회원 UUID가 없다.
5. 확인 후 DB 삭제를 확정하고 204를 반환한다.

저장·다시 읽기·암호화에 실패하면 `503 WITHDRAWAL_JOURNAL_UNAVAILABLE`을 반환하고 DB 삭제를 취소한다. 사용자는 탈퇴를 재시도해야 한다. 외부 요청이 서버에서 완료됐지만 응답이 끊기는 경우에는 기록이 남을 수 있다. 기록 저장 후 DB 확정이 실패한 경우에도 기록을 지우지 않는다. 복구 시 이런 **재인증을 거친 삭제 의사**까지 삭제 대상으로 처리한다. 따라서 503이 반드시 외부 기록의 부재를 뜻하지는 않는다. DB와 B2를 하나의 원자적 트랜잭션으로 처리하는 구조는 아니다.

외부 저장소 장애 중에는 탈퇴를 완료할 수 없다. 이를 우회하려고 기록 설정을 끄거나 직접 DB만 삭제하면 이후 백업의 완전성 판단을 중단해야 한다. 계정이 남는 확정 실패는 재시도로 정리하고, 운영자가 임의로 삭제 기록을 지우지 않는다.

암호화는 절대 경로의 age 실행 파일을 사용하고 자식 프로세스에 DB·B2·Google 환경 변수를 전달하지 않는다. 평문은 메모리에서 처리하며 서비스에는 복호화 개인키를 주지 않는다. [age 사용법](https://github.com/FiloSottile/age).

## 저장소와 키 준비

기존 `stelody-backups`와 별개의 **Private** 버킷을 만든다. 예시 이름은 `stelody-withdrawals-<고유 문자열>`이다. 기존 백업 키의 접근 범위를 넓히지 않는다.

버킷의 사용자 정의 수명 주기를 다음처럼 설정한다.

| 항목 | 값 |
| --- | --- |
| File name prefix | `stelody/withdrawals/records/` |
| Days from uploading to hiding | `8` |
| Days from hiding to deleting | `1` |

`coverage.json`에는 수명 주기를 적용하지 않는다. 기록 경로의 상위·하위 경로에 겹치는 다른 삭제 규칙도 만들지 않는다. B2는 숨김·삭제·고립된 숨김 표시 정리를 별도 S3 규칙으로 반환할 수 있으며, 도구는 이를 함께 검사한다. [B2 S3 규칙 변환](https://www.backblaze.com/apidocs/s3-get-lifecycle-configuration).

백업의 최대 유효 기간은 7일이다. 기록은 요청 후 8일 동안 복구 삭제 목록에 반영한다. 실제 파일은 8일 후 숨김, 숨김 후 1일 뒤 삭제 대상이 된다. 수명 주기는 하루 단위로 처리하므로 실제 삭제는 더 늦을 수 있다. 오래된 기록이 정상적으로 숨겨지는 것은 현재 백업의 복구를 막지 않는다. 필요한 기록이 일찍 숨겨지거나 최근 숨김 표시의 원인을 확인할 수 없으면 복구를 거부한다. [B2 수명 주기](https://www.backblaze.com/docs/cloud-storage-lifecycle-rules).

운영 웹 서비스용 Application Key는 해당 버킷 하나, `stelody/withdrawals/` prefix, **Read and Write**로 만든다. 버킷 ACL·수명 주기 읽기와 객체 저장·읽기가 필요하다. 모든 버킷 이름 나열은 사용하지 않는다. 복구에는 가능하면 별도의 같은 범위 **Read Only** 키를 사용한다. Master Key를 사용하지 않는다. [B2 키 권한](https://www.backblaze.com/docs/cloud-storage-s3-compatible-app-keys).

## 운영 활성화 순서

먼저 해당 릴리스를 배포한다. 새 B2 키 전달과 Render 설정 적용은 운영자의 승인을 받아 진행한다. 아래 값은 Render Environment에 넣으며 GitHub에 올리는 예시 파일에는 비밀 값을 넣지 않는다.

| 환경 변수 | 값 |
| --- | --- |
| `WITHDRAWAL_JOURNAL_ENABLED` | 활성화할 때 `true` |
| `WITHDRAWAL_B2_ENDPOINT` | 새 버킷 화면의 HTTPS S3 endpoint |
| `WITHDRAWAL_B2_BUCKET` | 새 버킷 이름 |
| `WITHDRAWAL_B2_ACCESS_KEY_ID` | 전용 keyID |
| `WITHDRAWAL_B2_SECRET_ACCESS_KEY` | 전용 applicationKey |
| `WITHDRAWAL_AGE_RECIPIENT` | 기존 복구 키의 **공개** recipient |
| `WITHDRAWAL_LEDGER_ID` | 이 기록 집합에 한 번만 생성한 UUID |

Docker에는 age가 설치되며 기본 실행 경로는 `/usr/bin/age`다. 별도 환경에서만 `WITHDRAWAL_AGE_BINARY`를 지정한다. 접속 주소·키·recipient·UUID가 잘못되면 활성화된 서비스의 기동 또는 탈퇴 처리가 실패한다. 개인키를 Render·GitHub·이 파일에 넣지 않는다.

1. 새 버킷과 키를 준비하고 위 설정을 적용한다. 기록 시작 파일이 없을 때 활성화된 앱은 탈퇴를 503으로 거부한다.
2. **모든 웹 인스턴스가 이 기능을 켠 릴리스로 전환됐고 이전 인스턴스·직접 삭제 경로가 멈췄는지 확인한다.** 무중단 배포 중 이전 인스턴스가 탈퇴를 처리할 수 있으므로 새 인스턴스 하나의 기동 성공만으로 판단하지 않는다.
3. 비공개 로컬 환경에 같은 `WITHDRAWAL_B2_*` 네 값과 Python 3.11+·boto3를 준비한다. 단일 작업으로 다음을 실행한다. `ledger-id`는 Render와 동일하다.

```sh
python3 infra/backup/withdrawals.py initialize \
  --ledger-id <기록-집합-UUID> \
  --confirm-all-writers-recording
```

빈 기록 경로에 `stelody/withdrawals/coverage.json`을 만들고 같은 객체 버전을 읽어 확인한다. 여기에는 공개 식별자와 기록 시작 시각만 있다. 기존 파일이나 숨김 표시가 있으면 덮어쓰지 않는다. 동시에 초기화하지 않는다.

4. 전용 시험 계정의 탈퇴로 저장과 삭제를 검증한다. 실제 사용자 계정을 시험으로 삭제하지 않는다.
5. **기록 시작 시각 이후에 새 백업을 만든다.** 이전 백업은 누락 여부를 소급 증명할 수 없어서 이 도구로 복구를 허용하지 않는다.

활성화 이후 설정 중단, 기록 직접 삭제, 이전 릴리스 재기동 등 누락 가능성이 생기면 `--confirm-continuous-recording`을 사용하지 않는다. 새 버킷·기록 집합으로 전환하고 전환 이후 백업부터 다시 검증한다. 문서의 플래그는 운영자가 실제 확인한 연속 기록 사실을 나타내며, 프로그램이 관측하지 못한 누락까지 증명하는 장치는 아니다.

## 복구 시 삭제 목록 만들기

웹·수집·내보내기와 직접 DB 변경 경로를 모두 멈춘다. 유효한 암호화 백업을 기존 `offsite.py unseal`로 해제하고, 복구 PC에 읽기 키의 `WITHDRAWAL_B2_*` 값과 `BACKUP_AGE_IDENTITY_FILE`을 준비한다. 개인키는 600 권한의 일반 파일이어야 한다.

```sh
python3 infra/backup/withdrawals.py reconcile \
  --backup /비공개/복구-백업-폴더 \
  --services-stopped-at <실제-중지-확인-시각-및-시간대> \
  --confirm-continuous-recording \
  --output /비공개/withdrawals.json
```

중지 확인 후 30분 안에 수행한다. 30분을 넘기면 모든 경로가 계속 멈춰 있는지 다시 확인하고 새 확인 시각으로 재실행한다. 출력 폴더는 700, JSON은 600이며 기존 파일은 덮어쓰지 않는다. 표준 출력에는 회원 UUID가 나오지 않는다.

도구는 기록 시작 기준의 단일 버전, 백업 유효 기간, 모든 페이지의 모든 객체 버전, 암호문 무결성·기록 집합·시각·보존 메타데이터를 확인한다. 설정·연속 기록·시계가 올바르다는 전제에서 보존 기간 안의 삭제 의사를 합쳐 기존 `database.py restore --withdrawals`가 읽는 파일을 만든다. 백업보다 앞선 의사도 포함해 저장 후 DB 확정 실패 사례를 다룬다. 정상적으로 만료된 의사는 제외한다.

시작 기준이 바뀌었거나 백업이 기준보다 오래된 경우, 손상·상충하는 기록, 불명확한 숨김 표시, 미래 시각 또는 중지 후 기록이 있으면 거부한다. B2에서 버전과 표시를 모두 강제로 지운 사실은 이 검사만으로 탐지할 수 없다. 연속 기록·수동 삭제 금지·키 접근 관리 확인이 필요하다.

생성한 파일로 [기존 복구 절차](deployment-operations.md#복구-순서)를 진행한다. 별도의 빈 DB로 복원하고 잔존 자료·권한·로그인을 검증한 뒤 공개 재개를 판단한다. 삭제 목록 생성 성공은 운영 DB 복원이나 트래픽 재개 완료를 뜻하지 않는다.

## 검증 범위

단위·통합 테스트로 실제 age 암호화·복호화와 변조 거부, 잘못된 저장소/보존 규칙/시작 기준 거부, 정확한 버전 읽기, 저장 실패 시 DB 삭제 취소·재시도, 동시 탈퇴, 기록 후 DB 확정 실패를 검증한다. Python 시험은 모의 B2의 페이지·버전·시각 경계를 검사하고 실제 age로 별도 시험 키를 사용한다.

2026-10-07~08에 전용 버킷·키·Render 활성화, 실제 서비스 중지를 확인한 시작 기준 생성, 새 GitHub 백업, 시험 계정의 운영 탈퇴와 암호화 기록 읽기, 대조 CLI 및 별도 빈 DB의 공식 복구를 검증했다.

10월 8일에는 운영자의 별도 시험 계정으로 실제 Google 재인증 왕복을 확인했다. 재인증 응답 true·DB CONFIRMED, 탈퇴 204·다음 계정 조회 401, 회원·개인 자료·세션 잔여 0행과 새 B2 암호화 기록을 확인했다. 일회성 실패 시험의 알림 이메일 수신도 운영자가 확인했다. 예약 백업 #17은 승인 대기 후 수동 재시도에서 새 백업 생성·암호화·B2 업로드·읽기 검증에 성공했다.

남은 관찰은 다음 무인 예약 백업 실행과 보존 기간이 지난 객체의 실제 수명 주기 삭제다. 상세 범위와 기준 시각은 [운영 검증 기록](operations-verification.md)을 따른다.
